## §1 红线（任何任务都不许越过）

### 1.1 产品红线

1. **零真实写**：AI 不得在真账号上发评论/私信/收藏/点赞/动态。所有验证走 `--fixtures` 或 `dryRun`。真实写只能由用户本人在面板上点。
2. **写默认关**：`share.enabled`、`like.enabled`、`dynamic.enabled`、`listen.*` 的默认值只能是 `false`；`safety.dryRun` 默认 `false` 但不得被任何新代码绕过。
3. **主人 ≠ 登录账号**：所有 `@ / 私信 / 聊天` 必须走 `src/account/owner.ts` 的 `resolveOwner()`，**不许回退**到登录账号。
4. **不删用户数据**：任何「清理/重建/恢复」都必须先备份；`secrets.json` 永不进备份（除非显式 `--with-secrets`）。
5. **不代用户决定**：涉及「夜里要不要收消息 / 错过窗口要不要补跑 / 恢复前要不要快照」这类偏好，**停下来问**，不要自己选。

### 1.2 工程红线

1. **不改测试来让测试通过**。测试挂了先判断：是测试写错了（过时口径），还是代码错了。改测试必须在提交信息里写清「为什么原断言不再成立」。
2. **不动 `.ps1` 的 BOM**：`packaging/*.ps1` 必须 UTF-8 **带 BOM**（PowerShell 5.1 靠它认中文）；`.json` 必须**不带** BOM。有不变式测试守着。
3. **写中文/模板字符串的文件，用 `write`/`edit` 工具，不要用 PowerShell 的 `Set-Content`/here-string**。
   > 真实事故（2026-10-22）：用 PowerShell 做字符串替换时把「空格」替换成了 `*`，一次废掉 7 个源文件。恢复靠 `git checkout` + 逐项重做。
4. **一次只改一个主题**：一个提交只解决一类问题；跨主题的改动拆开，否则回滚不了。
5. **原子写**：所有 JSON 状态用 `writeJsonAtomic`；不许直接 `fs.writeFileSync` 覆盖状态文件。
6. **凭据永不落日志**：任何新日志都走 `Logger`（自带脱敏）；诊断包最后过 `redactDeep`。
7. **写接口只有一个文件**：B 站写接口只许出现在 `src/bili/write.ts`；发评论只许 `share.ts`/`pending.ts`，删评论只许 `manual.ts`，收藏只许 `fav.ts`，点赞/动态只许 `like.ts`，私信只许 `dm.ts`/`chat.ts`/`manual.ts`/`share.ts`（有不变式测试）。
8. **不做体验降级**：不许为了「好看」删掉状态、确认、前置条件、错误原因。

### 1.3 交付红线

1. 每个任务结束必须：`npx tsc --noEmit` 干净 + `npm test` 全绿 + 相关 smoke（`offline`/`rehearse`/`bench` 按改动范围选）。
2. 每次改动都要在 `docs/审计处理记录.md` 或本文件 §10 留一行：改了什么、为什么、验收证据。
3. 提交信息用中文，说「为什么」而不是「改了什么文件」；格式参考已有提交（`fix(...)` / `feat(...)`）。

## §2 工作方法（每个 bug 都按这个流程走）

```
① 复现/定位：找到代码位置（文件:行号）或写出失败用例
② 判定：真实吗？影响和描述一致吗？（不一致就写清差异）
③ 决定：改 / 不改（不改必须写原因，并标进「暂缓」）
④ 最小改：只改必需的那几行；顺手重构要单开一条
⑤ 回归：先跑相关用例，再跑全量；新行为要加用例
⑥ 记录：处理记录 + 提交信息（含「为什么不那样改」）
```

**判定的四个桶**（与 `docs/审计处理记录.md` 一致，未修的 56 条都在这四类里）：

| 桶 | 含义 | 处理 |
|---|---|---|
| A 待拍板 | 需要用户定交互/口径 | 问，不猜 |
| B 待真机 | 需真账号/真网络才能验证 | 标记，等真机 |
| C 不改 | 设计取舍，影响可接受 | 写理由 |
| D 可选 | 改不改都行 | 标「暂缓」，不排期 |

> **用户的明确要求（2026-10-22）**：这一轮**只改「真耽误功能」或「会卡死/后果更严重」的**；其余**不是永远不改**，而是在处理记录里**打标记**，以后再说。

**标记机制（必须执行）**：在 `docs/审计处理记录.md` 的每条未修项后加一列 `状态`，取值只能是：
`已修` / `暂缓(P0外)` / `待真机` / `待拍板` / `不改`。
每次改动后，`README.md` 的「已知限制」要与这套状态保持一致。

## §4 P0 清单（只做这 6 件，做完就停）

### P0-1 抽帧的「假信号」

**现象**：体检里 ffmpeg 打勾，但报告写「不抽帧：模型是纯文本的」——用户会以为「装了 ffmpeg 就会看画面」。
**根因**：`src/config/spec.ts` 仍保留 `media.ffmpegPath`，`src/doctor.ts` 仍检查 ffmpeg；而 DeepSeek 是纯文本模型，画面永远进不了提示词。
**要做的**：
1. 删除配置里的整个 `media` 组（`spec.ts`），并确认面板/导出/校验没有残留引用。
2. 删除 `doctor.ts` 的 ffmpeg 检查项（以及它的 ✓/✗ 报告行）。
3. 报告里那句改成人话：`不看画面：模型只读标题/简介/字幕/评论`（一次即可，不要每轮重复刷屏——同一句每份报告最多出现一次）。
4. 手册/README 同步：不再提 ffmpeg。
**验收**：面板设置里搜不到 `ffmpeg`/`抽帧`；体检输出里没有 ffmpeg 行；`npm test` 全绿；`npm run offline` 的报告里那句话只出现一次。
**更正（2026-10-22 晚）**：上面「模型不支持图片」的判断是**错的**。DeepSeek 官方 Vision 文档写明
`deepseek-flash` 接受图片（JPEG/PNG/GIF/WebP，每张 ≤1024 tokens，支持 base64/URL/Files API）；
参考项目 `dsh-bili-whale` 的 `debrief.mjs` 也确实抽帧，并把九宫格交给模型读。

所以本项拆成两步：
- **已做（止损）**：先删掉「打了勾但永远不生效」的开关，不让它继续骗人；
- **待做（真实现）**：按 §7.10 把「看画面」真正做出来，做完再恢复配置项（届时叫「看画面」，默认关）。

**不许做**：不要只把配置加回来而代码依旧不抽帧（那就是回到骗人状态）。

### P0-2 通知渠道：中文名 + 只露两个 + 可测试

**现象**：用户在通知配置里看到 `file / webhook / command / dm / format / template / sendSummary…`，不知道选哪个，因此**没测**。
**要做的**：
1. 面板主界面只显示两个渠道，用中文：
   - **「B 站私信」**（内部 `dm`）—「把结果发到你的 B 站私信（最常用）」
   - **「本机日志」**（内部 `file`）—「写在程序目录的日志里，不打扰你」
2. 其余（`webhook`、`command`）折叠进「高级（一般不用改）」；展开时每个字段给一句中文说明 + 一个可复制的例子。
3. 每个渠道旁加 **「发条测试」** 按钮：`POST /api/notify/test`（要 CSRF），走 `dispatchNotifications()` 只发一条测试文本。
   - **用户已确认的口径**：允许在预演（`dryRun`）下发测试（只写日志/只打印）；**写开关关着 / 急停 / 风控冷却时一律不许真发**，返回人话原因。
4. 配置项描述全部改成中文（`spec.ts` 的 `label/desc`），**面板不出现英文枚举值**。
**验收**：面板上肉眼看不到 `webhook/command/format/template`；`dryRun` 下点「发条测试」只在日志里出现、不会真发私信；关掉写开关时按钮返回「写操作关着」。
**不许做**：不要删掉 webhook/command 的能力（用户以后可能用）；不要伪造「发送成功」。

### P0-3 动态发布 / 删自己评论：补入口（否则功能不可达）

**现象**：`publishDynamic()` 与 `DELETE /api/comments/:bvid/:rpid` 都有后端，但面板没有按钮；`dynamic.enabled` 打开也没用。
**要做的**：
1. **「发动态…」** 的入口（位置由 AI 结合 UI 定，用户无特殊要求）：放在**概览页「本轮挑中」卡片**里（每条视频旁），报告页对应记录旁也放一个小入口。
   点击 → 弹确认框（显示将发文案，**允许编辑**）→ `POST /api/dynamic`（新增）→ 成功/失败都在页面显示原因。
   - 硬性：必须 `dynamic.enabled` 为真、必须二次确认、每天 ≤1、`dryRun` 时只打印；**服务端再判一次**，不能只靠前端。
2. **「删除…」**（删自己发过的评论）：在报告页/账本「我发过的评论」旁；只对**账本里存在且 `type==='comment'`** 的 rpid 显示；
   **二次确认 = 必须输入「删除」两个字才可点**（用户已确认）。复用已有 DELETE 接口。
3. 两个按钮在 `dryRun` 下都走预演并在结果里标「预演」。
**验收**：开 `dynamic.enabled` + 关 `dryRun` 时能发一条（先在 `--fixtures` 下验证请求形状）；`dryRun` 下只打印；不在账本里的评论没有删除按钮；未输入「删除」时删除按钮不可点。
**不许做**：不要做「批量发/批量删」；不要给动态加定时。

### P0-4 报告必须能回答「今天为什么没做 X」

**现象**：默认开启的收藏可能几天才触发一次；用户看不到原因，只会认为「坏了」。
**要做的**：报告末尾加一小节 **「今天为什么没做」**，对 收藏 / 点赞 / 动态 / 私信分享 / 私信通知 / 评论监听 各给**一句结论**，取值只能是：
`开关关着` / `今天额度用完了` / `模型没提` / `提了但理由不够（<6 字/没说明同类）` / `同视频还在冷却` / `闸门拒绝：<原因>` / `已经是第 N 条` / `主人没配置` / `这一轮没跑（跳过）`。
数据来源：各执行器返回的结构化结果（不要从中文文案里正则抠）。
**验收**：任意一份报告都能回答「今天收藏为什么没发生」，且不出现「未知」「其他」这种废话。
**不许做**：不要每轮把 6 条都写成大段解释（一行一条，超过 6 条折叠）。

### P0-5 文档与计数对齐（5 分钟的事，顺手做）

1. `docs/审计处理记录.md` 顶部计数改为实际值：一级 16（修 13 / 部分 2 / 未修 1）、二级 41（修 23 / 部分 1 / 未修 17）、三级 46（修 6 / 部分 2 / 未修 38），**未修合计 56**，并按 §2 加 `状态` 列。
2. README / CHANGELOG / 需求文档 §15 的用例数统一为实际值（以 `npm test` 输出为准）。
3. 删掉「96 个字段」这类会漂移的硬数字，改成「字段由 `config/spec.ts` 自动生成」。
**验收**：三处数字一致；`grep -n "301 个用例"` 无命中。

### P0-6 当天已经过去的时刻不许排进计划（但**不补跑**）

**现象**（审计 3.28）：机器上午关着、下午才开时，程序会把「上午已经过去的时刻」排进当天计划，然后立刻判 `missed` —— 面板说「今天醒 2 次」，实际一次都不会醒。
**用户已确认的口径**：**过了就过了，不补跑**；但当天**剩余**的窗口仍然要能正常醒。
**要做的**：
1. `src/scheduler/plan.ts` 的 `generateDayPlan` 增加「已过时刻过滤」：只排 `atMs > now` 的槽位；被滤掉的时段不占当日额度，也不写 `missed` 事件。
2. 计划日志/面板文案写清：`今天还剩 N 次（已错过 M 次，不补）`。
3. 跨零点的尾巴（昨天排的、今天还没到点）**保留**——那不叫补跑，是当天的正常槽位。
**验收**：新增用例——「窗口 09:00–12:00、14:00 才启动 → 计划里只有未来的槽位，且醒来次数与剩余次数一致」；再跑一遍 `npm run soak`（7 天）确认每日 ≤3 不被破坏。
**不许做**：不要实现「补跑」；不要为了凑数把 `missed` 改成 `fired`。

## §5 P1：界面重做（文案为主，视觉为辅）

### 5.1 文案规范（最重要）

**目标读者**：能自己下载、愿意配置，但**不懂这个项目、不懂技术**的人。不是小白，也不是工程师。
**标准**：一眼知道「这一栏是干什么的、填什么」；技术细节放小字/`?` 里，不删。

| 规则 | 说明 | 反例 → 正例 |
|---|---|---|
| 标题用动词/名词短语 | 一眼知道在填什么 | 「分享渠道 via」→「**用什么方式分享**」 |
| 小字补充「影响/边界」 | 保留严谨，但别占主位 | 「静默时段」→ 大：**夜里别吵我**；小：这段时间只记日志，不发私信/webhook |
| 术语只出现在小字 | 主标题不许出现 `via/webhook/dryRun/token` | 「一律预演 dryRun」→ 大：**只演练，不真发**；小：打开后所有写操作只打印（内部字段 `safety.dryRun`） |
| 数字带单位与范围 | 别让用户猜 | 「每日上限 3」→「**一天最多发几条**（0–10，建议 3）」 |
| 危险操作说后果 | 不是「确定/取消」 | 「恢复默认」→「**把这些设置改回出厂值**（不会动你的账号、密钥、写开关）」 |
| 不哄小孩 | 不用感叹号、不用「只需一步」 | 「轻松搞定」→ 直接说做完会发生什么 |

**必须补齐的对照表**（交付物之一）：`docs/文案对照表.md`，三列 = `字段路径 / 现在（技术） / 改成（人话+小字）`，覆盖 `config/spec.ts` 的**每一个**字段。用户会逐行看。

### 5.2 视觉规范（明日方舟风格，但只借语言、不抄素材）

**依据**（公开资料，只取原则）：
- [《明日方舟》UI/UX 分析](https://www.hxsd.com/information/10926/)：信息分层、留白、几何切角、克制的强调色。
- [ark-ui 设计语言（基于公开证据的复刻规范）](https://github.com/Brandon030722/ark-ui-skill/blob/main/SKILL.md)：`ark` 家族 = 黑白 + 单一青色强调；**明确禁止**「随机六边形、终端噪点、扫描线、霓虹渐变、假系统代号」；`depth` 分 4 级（1 极简 / 2 中等 / 3 复杂 / 4 极繁）。
- 我们的选择：**family = ark，depth = 2（中等）**。理由：这是工具不是游戏，深度 3+ 的「仪表盘/多区舞台」会压过内容。

**Design tokens（初稿，实现时以原型为准）**：

| 类别 | 值 |
|---|---|
| 底色 | `#0B0D10`；面板 `#12161B`；浮层 `#171C22` |
| 线 | `#2A3138`（1px）；强调线 `#3E4A55` |
| 文字 | 主 `#E6EDF3`；次 `#9AA7B4`；弱 `#6B7885` |
| 强调 | 青 `#5FE0D8`（只用于「当前/可点/进度」，全站一个） |
| 状态 | 成功 `#5FD08A`；警告 `#E8C05A`；危险 `#E5534B`（只给破坏性操作） |
| 字体 | 正文 `"Microsoft YaHei UI", "Segoe UI", system-ui`；数字/时间/`token` 一律等宽（`Consolas`/`ui-monospace`） |
| 字号 | 页标题 24/1.2；区块标题 16/1.3；正文 14/1.6；小字 12/1.5；数字 13 等宽 |
| 间距 | 4 / 8 / 12 / 16 / 24 / 32（只用这六档） |
| 圆角 | **2px**（不做胶囊、不做大圆角） |
| 动效 | 进入 120ms 淡入 + 上移 6px（`ease-out`）；数值变化 200ms；**禁止**弹跳/旋转/无限循环动效；必须遵守 `prefers-reduced-motion` |
| 布局 | 桌面最大 1200px 居中；左窄导航（200px）+ 右内容；窄屏（<820px）导航变顶部横条 |
| 网格 | 内容区 12 列，卡片只跨 4/6/12，不出现半列 |
| 可访问性 | 正文对比度 ≥ 4.5:1；键盘焦点可见（2px 青色外框）；图标按钮必须有 `aria-label`；不用颜色单独表达状态（配文字/图标） |

**硬性禁止**（来自 ark-ui 的 `Avoid`，照抄执行）：
- 不加无信息作用的装饰：六边形、扫描线、噪点、乱码、假的「SYSTEM ONLINE」「LOAD 87%」、随机终端输出。
- 不把多种强调色混用（青 + 黄 + 品红 + 橙一起上）。
- 不用大标题+小灰字的「营销落地页」结构堆信息；状态优先于装饰。
- 不引入外部字体/CDN（离线可用是第一约束）。

### 5.3 执行顺序（避免九页全返工）

1. 先出 **2 页原型**：`概览` + `设置`（设置页挑 1 组字段做完整示范）。
2. 交付：`docs/ui/prototype-overview.png`、`docs/ui/prototype-settings.png` + 一段「和现在的差异」说明。
3. 用户点头后再铺其余 7 页；每页提交前跑 `test/ui-smoke.test.ts` 与 `test/ui-actions.test.ts`。

### 5.4 验收

- 文案：`docs/文案对照表.md` 100% 覆盖；抽查 10 个字段，非技术用户能说出「填什么」。
- 视觉：桌面 1440 / 窄屏 390 两个宽度截图无横向滚动、无文字碰撞；键盘 Tab 能走完主流程；`prefers-reduced-motion` 下无位移动画。
- 功能：所有按钮仍可用（`ui-actions` 用例）；没有因为改类名/结构导致 `querySelector` 失效。

## §6 P2：双击即用（方案 A：启动器 + 无地址栏窗口 + 托盘）

### 6.1 用户体验（这是验收标准）

1. 双击桌面/开始菜单图标 → **3 秒内**出现面板窗口（没有命令行窗口、没有地址栏、没有标签页）。
2. 直接关掉窗口 → 程序**还在跑**（托盘有图标，到点照常醒）；托盘右键「打开面板」能再开。
3. 再双击一次图标 → 只是把面板窗口带到前面，**不会**起第二个内核。
4. 开机自启 → 只出托盘（不弹窗、不抢焦点），内核自动起来。
5. 卸载 → 关掉内核、删程序、**保留数据**。

### 6.2 实现规格（不改内核协议）

| 部件 | 做法 |
|---|---|
| 启动器 | 双击目标改为 `BiliWhale.cmd`（或托盘 exe）：① 设 `BILIWHALE_KERNEL_CMD`（**路径带引号**）② 启动托盘（`--autostart` 可省）③ 托盘负责起内核并开面板 |
| 面板窗口 | 用系统 Edge 的 app 模式：`msedge.exe --app="http://127.0.0.1:<port>/?token=<token>" --window-size=1200,820`。地址从 `runtime.json` 读（已有 `url` 字段，**不要**自己拼 token） |
| Edge 探测顺序 | ① `%ProgramFiles(x86)%\Microsoft\Edge\Application\msedge.exe` ② `%ProgramFiles%\...` ③ 注册表 `HKLM\SOFTWARE\Microsoft\Windows\CurrentVersion\App Paths\msedge.exe` ④ 都没有 → `start "" "<url>"` 用默认浏览器（体验降级但可用） |
| 「关窗口不退出」 | 不需要拦截关闭事件：窗口是独立进程，关它不影响内核/托盘。**不要**试图 hook 窗口消息 |
| 单实例 | 内核已有 `InstanceLock`；托盘再加一个命名 Mutex（`Global\BiliWhaleTray`），二次启动只发「打开面板」请求 |
| 托盘菜单 | 打开面板 / 现在跑一轮（预演）/ 暂停·恢复 / 开机自启 / 打开数据目录 / 退出（退出=先请内核优雅退出，再退托盘） |
| 首启引导 | 内核没配主人 UID 或没 key 时，面板打开后直接在概览页显示「还差哪几项」并给跳转按钮（复用 `doctor` 的结果，**不要**每次轮询都跑 doctor） |

### 6.3 验收

- 把整包解压到 **含空格和中文** 的路径（如 `D:\我的 程序\BiliWhale`），双击能出窗口、能跑一轮（预演）。
- 关闭窗口后等 1 分钟，托盘仍在、`/api/health` 仍 200；到点（可用 `--fixtures` + 手动触发）仍能唤醒。
- 连点两次图标：`Get-Process node` 只有一个内核进程；`runtime.json` 的 pid 没变。
- 无 Edge 的机器（可临时改探测顺序模拟）：回退到默认浏览器，不报错、不弹命令行。
- `npm run rehearse` 仍 13 项全过。

### 6.4 不做

- 不做 WebView2 单 exe（用户已同意先 A；将来要单 exe 再单独立项）。
- 不做「关窗口=退出」的选项（会让人以为程序死了）。
- 不引入 Electron/Tauri。

## §7 P3：提示词精修（人设 / 日记与评论 / 私聊）

### 7.1 现状：提示词在哪

| 文件 | 管什么 | 现状问题 |
|---|---|---|
| `src/prompts/system.md` | 总人设（她是谁、怎么说话、底线） | 偏抽象，没有「不知道就别编」「一句话说一件事」这类可执行约束 |
| `src/prompts/charter.md` | 判据与克制（什么值得看/分享/收藏） | 与 system 有职责重叠，容易互相打架 |
| `src/orchestrator/prompts.ts` → `buildDeepPrompt` | **日记与分享文案的具体要求**（任务 5/6/7 + 输出示例） | 只有「散文体、别写成汇报」；没有长度、没有事实锚点、没有禁词 |
| `src/orchestrator/chat.ts` → `buildChatPrompt` | 私聊回复 | 硬编码在代码里；没有人设细节、没有长度/句长约束 |

### 7.2 用户已认可 / 不认可（2026-10-22）

| 认可 | 不认可 |
|---|---|
| 正例 + 反例（few-shot） | ❌ 固定三段结构（「我看到的→我怎么想→跟你的关系」） |
| 套话黑名单（硬约束） | ⚠️ 「写完自检」的方向认可，但**标准要可执行**，不能是「感觉好不好」 |
| 字数硬约束 | |

> 所以：**不规定段落数与顺序**，只规定「必须出现什么 / 不许出现什么 / 多长」。自检改成一张**可数**的检查表（见 7.4）。

### 7.3 三个资产各自要改什么

**A. 总人设 `system.md`**
- 加一节「她怎么说话」：句长上限、口癖（最多 2 个）、不用的词（见黑名单）、不用感叹号、不用客服腔。
- 加一节「她不知道什么」：不编视频内容、不编时间点、不编评论区；没有事实就写「我没看到」。
- 加一节「她不做的事」：不改设置、不承诺、不代替用户社交。
- **删掉**与 `charter.md` 重复的判据（判据只在 charter）。

**B. 日记与评论 `buildDeepPrompt`（按用户 2026-10-22 的明确要求重写）**

用户对日记的原话要求（逐条对应，不许自由发挥）：
> 核心目的是让它们尽可能像人真的刷完视频一样。不要求必须对每个视频作出怎样的评价，想写哪个写哪个，篇幅占比也随意，甚至关注点不在视频本身也可以。
> 唯独希望尽可能像真人一样，可能会有抱怨有感叹也可能没有，避免意味深长的抒情和莫名其妙的文艺范，言之有物和每句话之间的逻辑也很重要。
> 并不是说要写成逻辑严密的文字，只是希望就像真人一样有写的过程的思路，而不是东一句西一句。**每篇不高于 300 字**。

**必须写进提示词的规则（不规定段落数与顺序）**：
1. **长度**（用户 2026-10-22 定稿）：
   - 当天**非最后一轮**：公开日记 ≤300 字（当作「随手记」，只写这一轮看到的）；
   - 当天**最后一轮**：写一篇「今天的日记」≤**800** 字（可整合前面几轮的观察，但不许复制前面段落的原句）；
   - 一天只醒一次时：只写那一篇 800 字，不再另写 300 字；
   - **私密日记**：每轮 ≤**500** 字（可以比公开日记更直白）。
2. **不逐条点评**：可以只写其中 1–2 条，其它一条带过或不提；篇幅不平均是正常的。
3. **允许跑题**：可以写自己的事（冰箱里有几个鸡蛋、桌上堆了什么、明天要上课），只要跟"刚看完的东西"有自然的连接。
4. **可以有情绪也可以没有**：抱怨、感叹、"算了"都行；**但禁止**升华、抒情、文艺腔、金句（见 7.5 黑名单）。
5. **言之有物**：至少 **2 个只有真看过才知道的细节**（一句原话 / 一个数字 / 评论区某个具体说法 / 一个具体画面）；不许写"内容很精彩""受益匪浅"这种放之四海皆准的话。
6. **思路要连贯**：句子之间要有推进（因为/所以、本来…结果、看到 A 想到 B），**禁止**东一句西一句的并列清单；但不要求议论严密、不要求有结论。
7. **结尾可以是一个具体动作或状态**（"先去洗澡"、"今晚把桌面清出来"、"明天还得上课"），**不许**是总结、鸡汤、展望。
8. **只准写程序真的做过的事**：程序只能读标题/简介/字幕/评论。所以日记里**不许出现**「我点进主页看了看」「我去搜了下」「我关注了」「我买了」这类**没有发生过**的动作（见 7.4 第 8 项检查）。
9. **按工具实际读到的写**：只写本轮工具真的返回过的内容（标题/简介/字幕原文/评论原文/播放量这类数字，见 7.9）。
   工具没给的信息（画面细节、别人的主页、搜索结果里没有的东西）不写；没发生过的动作（点进主页、搜索、关注、购买）不写。
10. **写"反应"，不写"来源标注"**：可以像人一样被内容触发——"看着是真香""我本来没觉得多饿""这个我来回看了几遍"。
    **不要**每句都加"字幕里说""简介里写着"这种报告腔（用户 2026-10-22 明确：这会**加重** AI 味）。
    只有确实需要区分「他说的」和「我猜的」时才点一句来源，一篇里最多 1–2 次。
11. **拿到的材料不够时，写"没看到"或换个角度，不要编**：例如字幕没拿到，就写"这条没字幕，只看了标题和评论"。

**评论（分享文案）**：≤ `maxChars`、一句话只讲一个点、必须有具体所指（哪句话/哪个点）、`@` 只 `@` 主人一次、不带链接与价格、不写"推荐大家看看"。

**few-shot**：**2 篇正例**取自用户提供的真实日记（见 7.6），**1 篇反例**由 AI 按"AI 味"写出来、交用户确认后再用。正例不许 AI 改写。

**C. 私聊 `buildChatPrompt`**
- 口语、≤500 字、一次只回一件事、最多一个问句；
- 不重复对方的话、不用「首先/其次」、不用客服收尾；
- 被问「你能干嘛」时给 3 条真实能力（聊天/发今天的公开日记/发今天视频的信息），不吹。
- 把提示词从 `chat.ts` 挪到 `src/prompts/chat.md`（可读、可改、可被用户自己编辑），代码只读文件。

### 7.4 自检：改成可数的检查表（每条都是「是/否」，不是「好不好」）

生成后由代码做**确定性检查**（不是模型自评），不过就重写一次（最多一次），再不过就用旧文本并标注：

| # | 检查 | 判定方式 | 打回后怎么办 |
|---|---|---|---|
| 1 | **字数 ≤300** | 中文字符数（含标点） | 让它压到 260–290 再交 |
| 2 | 无黑名单词 | 字符串命中（7.5 的表） | 替换/删句 |
| 3 | 单句 ≤45 字 | 按 `。！？；\n` 切分逐句 | 拆句 |
| 4 | 事实锚点 ≥2 | 至少 2 句含「数字 / 引号 / 时间词 / 具体名词（品牌、物件、动作）」；正则粗判 + 人工抽查 | 补一个具体细节 |
| 5 | 没有重复句式 | 相邻 3 句开头 2 字不得全同；「的」连用 ≤2 | 改开头 |
| 6 | 结尾不是总结/鸡汤 | 最后一句不命中黑名单「总结类」；且**必须**是具体动作/状态/时间之一 | 换成动作 |
| 7 | 评论/私聊不超长、`@` 只一次 | 字符数与 `@` 计数 | 截断 |
| 8 | **没有工具做不到的动作** | 命中「点进主页/搜了他的/去搜/关注了/点赞了/买了/下单了/看了第二遍/进了直播间」→ 打回（工具没有这些能力） | 换成你实际做过的（看评论、看简介、看字幕）或删掉 |
| 8b | **没有报告腔** | 「字幕里说/简介里写着/标题提到」这类来源标注，一篇里 >2 处 → 打回 | 改成直接转述（"他说面是自己擀的"） |
| 9 | 私密日记含偏好校准 | 必须出现"下次往哪偏"的一句（这条是产品要求，不是文风） | 补一句 |

> **明确不做的「自检」**：不让模型自评「有没有逻辑」「像不像人」——那是主观判断，模型自评会给你一个「很好」的假答案。
> **人工只判断一件事**：「读起来像不像一个人在记事」（用户做，AI 不自评）。

### 7.5 黑名单（初稿，来自公开的 AI 写作特征研究，中英各一份）

依据：[Wikipedia:Signs of AI writing](https://en.wikipedia.org/wiki/Wikipedia:Signs_of_AI_writing)（总结「拔高意义、空泛分析、宣传腔、总结收尾」等模式）、[中文 AI 写作模式目录](https://github.com/0xtresser/cn-humanizer/blob/main/references/cn-ai-patterns.md)（18 类中文套话）。

**中文（命中即打回）**：
`综上所述` `总而言之` `总的来说` `由此可见` `值得一提的是` `值得注意的是` `不可否认` `毫无疑问`
`不仅…而且` `既…又…` `一方面…另一方面` `首先…其次…最后`
`赋能` `深耕` `助力` `打造` `引领` `全方位` `多维度` `一站式` `闭环` `抓手` `底层逻辑` `顶层设计`
`具有深远意义` `里程碑` `新篇章` `开创性` `令人振奋` `欣欣向荣` `未来可期` `拭目以待` `前景广阔`
`希望以上` `如有疑问` `仅供参考` `不当之处`

**英文**：`delve` `tapestry` `testament` `not just X, but Y` `it's important to note` `in conclusion` `overall,` `plays a vital role` `underscores` `showcases`

**文艺腔 / 抒情腔（用户明确讨厌的「莫名其妙的文艺范」）**：
`仿佛` `宛如` `像是…的隐喻` `时光` `岁月` `温柔` `治愈` `仪式感` `生活的意义` `生命的重量` `在这个快节奏的时代` `值得被记录` `留一点空间给自己` `与自己和解` `情绪的出口` `被看见` `细碎的美好` `烟火气`

**结构类禁令**：不用「总结段」；不用「三个排比收尾」；不用「每段先总后分」的固定节奏；不用 Markdown 列表写日记（报告可以）；不用感叹号堆情绪；**不许**把一天的日记写成"逐条点评清单"。

### 7.6 正例库（用户提供的真实日记，few-shot 素材，不许改写）

来源：用户 2026-10-22 提供的一整天记录（原文 12 段，约 1600 字）。这里只摘 2 段做 few-shot，其余存进 `src/prompts/examples/diary-*.md` 供以后换用。

**正例 A（食物 + 自我修正 + 生活动作收尾）** — 用户原文，**不改写**：

> 刷到一个人做油泼面，面条是他自己擀的，最后泼辣椒油那一下看着是真香。我本来没觉得多饿，结果看完就去翻冰箱了，只有两个鸡蛋和半袋挂面。
>
> 又刷到一个教做早餐的，说五分钟就能搞定。我看了下，他光切配菜就切了快两分钟，而且锅里那个东西明显提前煮过。现在短视频里的五分钟跟游戏宣传片里的实际画面一样，看看就行。最后我煮了碗面，没敢学油泼面，怕厨房弄得全是油。

**正例 B（跨条联想，不逐条点评，结尾是安排不是总结）** — 用户原文，**不改写**：

> 刷到一个人改造出租屋，原本屋里乱七八糟，换了窗帘、灯和桌子之后确实好看了不少。我点进主页看了看，发现他前后发了好几条，每次展示的角度还不一样，估计花的钱比标题里说的多。
>
> 我也想把自己的桌子收拾一下，但看了一圈发现最大的问题不是桌子不好看，是上面东西太多。昨天买的线材还堆在角落里，拆完包装就没管了。算了，今晚先把桌面清出来，别又看着视频下单一堆收纳盒，结果盒子也没地方放。

> **这两段怎么用**（用户 2026-10-22 定）：
> 1. 它们示范的是**写法和反应**——句子长短、口语词、"我本来…结果"、结尾落在生活动作上；
> 2. 里面具体看到什么、做了什么，以**本轮工具实际返回的内容**为准（见 7.9）。工具没给画面，就不要硬写画面细节；
> 3. 但**不要**为了"显得有依据"把"看着真香"改成"字幕里说…"——那是报告腔，用户明确说这样 AI 味更重；
> 4. 正例 B 里的"点进主页"是工具做不到的动作，写的时候换成你实际做过的（看评论/看简介），或直接删掉，**不要**换成"简介里列了…"这种句式。

**改写原则**（用户 2026-10-22 定）：例子只示范**写法和反应**，事实以「本轮工具实际返回了什么」为准（见 7.9）。
> 句子结构、口语词、收尾方式**照学**；看到什么、做了什么**按工具来**；但不写「字幕里说/简介里写着」这种报告腔。

**从正例里提取的「风格特征」**（写进提示词时要转成正面要求，不要照抄句子）：
- 句子长短不一，10–30 字为主，很少超过 40 字；
- 细节全是"我家的东西"（两个鸡蛋、半袋挂面、线材、收纳盒），不是对视频的复述；
- 高频口语：挺、倒是、估计、可能、反正、有点、算了、行吧、我本来…结果；
- 评价落在**具体行为**上（"他回了一句自己习惯了早睡"），不写"很有深度"；
- 跨条靠"又刷到 / 后面又刷到 / 最后"自然衔接，不写"第二条""综上所述"；
- 会有自嘲和抱怨，但**不升华**；
- 结尾是生活动作（煮面 / 清桌子 / 洗澡 / 明天上课）；
- 关于视频的描述都来自**本轮工具返回过的东西**（标题/简介/字幕/评论/数据），但不写"来源标注"；反应和感受随便写。

**反例（AI 按"AI 味"写，待用户确认后才进 prompt）**：留空，由 P3 执行时写 1 篇，交用户判断。

### 7.7 验收

1. 用正例 A/B 当 few-shot，生成 **3 篇**新日记；与用户的 **2 篇正例**并排，按 7.4 的 9 项逐条打勾，给出对比表。
2. 黑名单命中数：新文 = 0；**字数**：3 篇都 ≤300；**编造动作**：0 次。
3. 单句长度：≤45 字的句子占比 ≥90%。
4. 人工判断（用户做）：只有一项——「读起来像不像一个人在记事」。AI 不自评。
5. `maxTokens` 与预算不变（不要为了压字数调小，避免 JSON 被截断）。
6. 抽查：把 3 篇新日记和 2 篇正例混在一起，用户能否分辨出哪几篇是 AI 写的（能分辨 → 还没到位）。

### 7.8 日记粒度与字数（已定稿，2026-10-22）

用户选 **B**，并补充字数：

| 场景 | 写什么 | 上限 |
|---|---|---|
| 当天**非最后一轮** | 「随手记」：只写这一轮看到的（公开日记） | 300 字 |
| 当天**最后一轮** | 「今天的日记」：整合当天所有轮次（公开日记） | **800 字** |
| 一天只醒一次 | 只写那一篇「今天的日记」 | 800 字 |
| **私密日记**（每晚都写） | 给自己看 + 偏好校准 | **500 字** |

**落盘格式**（src/writers.ts）：
- 非最后一轮：`## <时间> · 随手记` + 正文 300 字；
- 最后一轮：`## <时间> · 今天的日记` + 正文 800 字（**不许复制**前面「随手记」的原句，只能接续/整合）；
- 私密日记：每天一篇，当天最后一轮写；上限 500 字，必须含「偏好校准：哪条视频、用户什么反应、下次往哪偏」。

**「最后一轮」怎么判**（src/scheduler 与 round.ts 共用）：
- 当天计划里**没有未触发的 wake 槽位**（全部 fired/missed），或当前时间已过最后一个窗口 → 视为最后一轮；
- 手动跑：若当天已无未来槽位，也算最后一轮；
- 边界：跨零点时按槽位所属的那一天算（昨天排的尾巴，仍算昨天）；暂停期间不产生新的最后一轮。
### 7.9 工具能力清单（写日记/评论/私聊时，只能用这些**真实返回过**的东西）

| 工具（`src/agent/tools.ts`） | 能拿到什么 | 能不能当事实写进日记 |
|---|---|---|
| `get_video_info` | 标题、简介、UP、时长、播放/点赞数、aid/cid | ✅ |
| `get_subtitles` | 字幕原文（**需要登录 cookie**；匿名常拿不到） | ✅（拿到才写） |
| `get_comments` | 热评、楼中楼原文与赞数 | ✅ |
| `search_videos` / `hot` / `ranking` / `following` | 候选标题、UP、数据（**不进候选池，只是参考**） | ✅（仅标题/数据层面） |
| **没有画面工具** | 抽帧/看图**不存在**（DeepSeek 是纯文本模型） | ❌ 别写"画面里/镜头/颜色"这类**具体视觉细节**；可以写"看标题/听字幕感觉…"这种**反应** |
| **没有主页/搜索他人/关注/购买** | 程序不会翻人主页、不会替他搜索、不会下单 | ❌ 写了就是编造 |

> 一句话：**事实用工具给的，反应用自己的。** 拿不到字幕时，就写"没字幕，只看了标题和评论"——这不丢人，比编画面强。
### 7.10 看画面（抽帧）实现规格（P0 之后第一件，学习参考插件）

**依据**
- [DeepSeek Vision 文档](https://api-docs.deepseek.com/guides/vision/)：`deepseek-flash` 支持图片，
  每张图按尺寸计 token（≤1024），支持 base64 data URL / 外部 URL / Files API；图片只能在 `user` 消息里。
- 参考项目 `tools/commands/debrief.mjs`（`Alterssss/dsh-bili-whale`）：六路互补（元信息/封面/字幕/弹幕热区/热评/抽帧），
  抽帧产出九宫格与「字幕条」长图，**交给模型读图**；脚本只备素材、不作判断。

**要做四件事**
1. **取视频**：`x/player/wbi/playurl` 拿一路低清 mp4（要 cookie）；下载到缓存目录，用完即删。
2. **抽帧**：ffmpeg 等距或场景检测取 9 帧 → 拼 3×3 一张图；无字幕轨时**额外**做「字幕条」
   （裁画面下方约 32%，每 7 秒一帧竖拼，等于把硬字幕读出来——参考项目的实测经验）。
3. **喂图**：`LlmClient` 增加 `image_url` 内容块（base64），深读请求带 `[{type:"text"},{type:"image_url"}]`。
4. **提示词与报告**：画面只作素材（别当唯一依据）；报告写「看了画面 / 没看（原因）」。

**硬性约束**
- **默认关**：`media.frames=false`；开了才下载/抽帧；ffmpeg 缺失、下载失败、超时 → 降级为纯文本，报告写原因，**不许**让整轮失败。
- 超时按视频时长算（参考项目踩过：25 分钟片子默认 120s 必超时）→ `120s + 时长 × 1.5`。
- 缓存限量（条数 + 总 MB），跑完删；**不把视频或图片放进报告/日志/诊断包**。
- 每张图 ≤1024 token，一次最多 2 张（九宫格 + 字幕条），并在 `runBudgetTokens` 里预留。

**验收**
- 用例：ffmpeg 不存在 → 不报错、报告写「没看画面：没装 ffmpeg」；
- 用例：图片内容块形状正确（`image_url.url` 是 `data:image/jpeg;base64,...`），且不进 system/assistant 消息；
- 夹具：给一段假 mp4/假 ffmpeg 输出，能生成一张 sheet 并写进 run 记录；
- 真机（用户）：开 `看画面` 跑一轮，报告与日记里出现只有画面才有的信息（例如硬字幕里的一句台词）。
